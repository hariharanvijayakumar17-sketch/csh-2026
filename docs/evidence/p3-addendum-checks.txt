- defaults seeded into `settings`: `ratelimit.login.ip_per_min=60`,
  `ratelimit.login.account_per_min=10`
- test proves runtime edit of the setting changes behaviour (set to 3 →
  4th account attempt rate_limited; set IP limit to 4 → 5th IP attempt
  rate_limited), i.e. NOT hard-coded
- per-account limit proven independent of IP (fresh IPs still rate-limited)

### item 2 — progressive delay keyed on (account, IP) (tests: "item 2")
- 3 failures from attacker IP → 4th attempt SLOWED even with correct
  password (30 s, doubling, cap 30 min; table `login_delays`, PK
  (user_id, client_ip))
- legitimate IP: immediate success, unaffected by attacker failures
- delay expiry → success; success resets that (account, IP) counter
  (2 further failures do NOT re-delay)
- old hard lockout removed: migration 0001 drops users.failed_attempts and
  users.locked_until (commit 0001_absent_mercury.sql)

### item 3 — scrypt costs (unit: password-params.test.ts)
- EXPORTED constants (verified by test): N=16384 (2^14), r=8, p=1, keyLen=64
- DUMMY_HASH parsed in test: same N/r/p, 64-byte hash (regenerated so the
  dummy's derivation length matches real hashes exactly)
- comparison uses crypto.timingSafeEqual; length-mismatched stored hashes
  rejected before compare (no throw) — regression test kept
- MEMORY LIMIT (documented): scrypt work area = 128·N·r = 16 MiB per hash.
  node:crypto runs scrypt in the libuv thread pool (default 4 threads,
  UV_THREADPOOL_SIZE). Worst-case concurrent = 4 × 16 MiB = 64 MiB.
  Safe on a 1 GB free-tier host; deploy doc sets UV_THREADPOOL_SIZE=4
  explicitly. Never raises N beyond 16384 without re-checking this.

## 2. TRUSTED_PROXY_COUNT — what happens if it is wrong (item 1 doc)
- The app NEVER reads x-forwarded-for unless the hop at the end of the
  chain is trusted. TRUSTED_PROXY_COUNT = number of trusted hops in front
  of the app (0 = no proxy; 1 = one reverse proxy, e.g. Caddy on the same
  host, which must APPEND its own x-forwarded-for entry).
- Set too LOW (0 behind Caddy): every request's client IP = the proxy's
  own IP (the socket peer). Consequence: the whole campus shares the
  proxy's socket address → the GENEROUS IP limit (60/min) becomes a
  global cap → false 429s during peak (e.g. registration day), and
  per-(account,IP) delays key on the proxy IP (still safe, less precise).
  Detection: audit log shows one IP for all users.
- Set too HIGH (e.g. 2 with only one proxy): the app trusts attacker
  control of the rightmost x-forwarded-for entry → an attacker can
  SPOOF client IPs, evade the IP rate limit and fragment the delay
  buckets. The P3 integration test proves spoofing is IMPOSSIBLE at
  TRUSTED_PROXY_COUNT=0 (rotated fake XFF values all land in one bucket).
- Default is 0 (fail safe). Set it to the exact trusted hop count at
  deploy time (P13); the value is not secret but is operationally critical.

## 3. Sandbox-only Postgres `trust` — cannot appear in production
- The sandbox cluster uses loopback `trust` so the test DB is reachable
  without a password. This is SANDBOX-ONLY (DECISIONS D14).
- Production config must use SCRAM-SHA-256 + real credentials; the
  production guard makes the difference unmissable: it (a) refuses
  loopback/dev-default DB URLs in production and (b) actively probes with
  an empty password — a trust-configured production DB would therefore
  refuse to start (proven above: the sandbox's trust DB is detected).
